1. INTRODUCTION                                         *hdlsnip-introduction*

hdlsnip.nvim renders VHDL from Lua templates rather than pasting it from a
static snippet file.

The difference matters where a snippet file cannot follow: the reset branch of
a clocked process sits outside the clock test when the reset is asynchronous
and inside it when the reset is synchronous, port columns align against
whichever name your clock has, and a vendor attribute differs per family.
Those are configuration, not typing, and getting them wrong is a synthesis
mismatch rather than a syntax error.

Templates come in two forms:

Static      Rendered either as plain VHDL or as an LSP snippet with tabstops.
Dynamic     The output depends on configuration or on a parameter, so it
            cannot be a snippet: a tabstop cannot decide whether a reset port
            exists. These prompt for their parameters and insert finished
            code. |hdlsnip.expand()| falls back to this automatically.

==============================================================================
2. REQUIREMENTS                                         *hdlsnip-requirements*

Neovim 0.10 or newer, for |vim.snippet|.

No plugins are required. Selection and prompting go through |vim.ui.select()|
and |vim.ui.input()|, so any picker you have installed is used, and the
built-in prompts are used if you have none.

3. COMMANDS                                                 *hdlsnip-commands*

                                                                    *:HdlSnip*
:HdlSnip [{name}]       Insert a template, prompting for each parameter.
                        Without {name}, a picker opens first. Completion
                        offers every registered template name.

                                                              *:HdlSnipExpand*
:HdlSnipExpand [{name}]
                        Expand a template as a snippet, so its parameters
                        become tabstops. A dynamic template cannot be a
                        snippet, so it prompts and inserts instead.

                                                         *:HdlSnipInstantiate*
:HdlSnipInstantiate [{name}]
                        Instantiate an entity from the project. Without
                        {name}, the entities found are offered. With a bang,
                        the port signals are added too. See
                        |hdlsnip-instantiate|.

                                                           *:HdlSnipTestbench*
:HdlSnipTestbench [{name}]
                        Write a testbench around an entity from the project.
                        Without {name}, the entities found are offered. See
                        |hdlsnip-testbench|.

                                                              *:HdlSnipReload*
:HdlSnipReload          Rescan the runtimepath for templates. Useful while
                        writing one.

                                                                *:HdlSnipEdit*
:HdlSnipEdit            Open a form for the parameters of the template under
                        the cursor. See |hdlsnip-editing|.

                                                           *:HdlSnipLspAttach*
:HdlSnipLspAttach       Attach the completion server to the current buffer.
                        Rarely needed: it attaches to VHDL buffers on its
                        own. See |hdlsnip-completion|.

4. MAPPINGS                                                 *hdlsnip-mappings*

Nothing is mapped unless `setup()` is called with `keys`. Every entry defaults
to `false`. >lua

    require("hdlsnip").setup({
      keys = {
        expand = false,
        jump_next = false,
        jump_prev = false,
        field_next = { "<Tab>", "<C-k>" },
        field_prev = { "<S-Tab>", "<C-j>" },
      },
    })
<

expand          Insert and select mode. Expands the trigger word before the
                cursor, or jumps forward when a snippet is already active. One
                key for "carry on", which is what most configurations bind.

jump_next       Insert and select mode. Only needed if you want a key for
                jumping forward that is separate from `expand`.

jump_prev       Insert and select mode. Jumps to the previous tabstop.

field_next      Moves to the next field in the parameter dialog. Buffer local
                to that window, so it affects nothing else. Takes one mapping
                or a list; defaults to `<Tab>` and `<C-k>`.

field_prev      The same, backwards. Defaults to `<S-Tab>` and `<C-j>`.

These two default to being set, unlike the rest, because they act only inside
a window the plugin opened and take no key away from you. Set either to
`false` to leave the dialog to the arrow keys.

Each mapping falls through when it has nothing to do, feeding the key back so
it does whatever it otherwise would. `<C-k>` therefore still inserts a digraph
when there is no trigger and no active snippet.

A completion plugin bound to the same key wins by definition order. Give
hdlsnip first refusal instead, for example with blink.cmp: >lua

    keymap = {
      ["<C-k>"] = {
        function()
          return require("hdlsnip").expand_at_cursor()
        end,
        "fallback",
      },
    }
<

5. COMPLETION                                             *hdlsnip-completion*

Templates appear in the completion menu through an in-process LSP server: a
Lua table rather than a process, started with |vim.lsp.start()| and costing
nothing when idle.

A server rather than a completion source because every frontend consumes LSP
already. One implementation covers the built-in menu, nvim-cmp and blink.cmp,
instead of three sources with three sets of bugs. It also composes with
`vhdl_ls`: both clients attach to the same buffer and the menu merges them, so
entity completions and templates appear together.

It attaches to VHDL buffers automatically. Set `lsp = false` to turn it off,
or use |:HdlSnipLspAttach| for a buffer it missed.

nvim-cmp and blink.cmp need no configuration. For the built-in menu, enable
completion when the client attaches: >lua

    vim.api.nvim_create_autocmd("LspAttach", {
      callback = function(ev)
        vim.lsp.completion.enable(true, ev.data.client_id, ev.buf, {
          autotrigger = true,
        })
      end,
    })
    vim.opt.completeopt = { "menuone", "noselect", "popup" }
<
With `noselect`, `<C-n>` selects an entry and `<C-y>` accepts it. Accepting
expands the snippet, so the first parameter is selected and ready to type
over.

Every template is offered. A static one expands as a snippet; a dynamic one
cannot, since a completion item asks no questions, so it inserts nothing and
opens the parameter dialog instead. The menu says which will ask.

The documentation popup previews the VHDL the template would render, cased
according to the configuration in effect for that buffer.

6. CHANGING A PARAMETER                                      *hdlsnip-editing*

A dynamic template prompts once and inserts finished code. |:HdlSnipEdit|
opens a form for the block under the cursor, listing its parameters; the block
re-renders as the form is edited.

The same dialog asks for the parameters in the first place: every field at
once, with what it accepts beside it, rather than a question at a time. A
value that does not validate is reported in a window above the dialog and the
dialog stays open.

The parameters are edited outside the generated code rather than inside it.
There is then no cursor to preserve in a block being replaced, and no
per-parameter region to track: the text is generated, so re-rendering from the
parameters is enough. No snippet engine is involved.

In the form, `<CR>` accepts and closes, `q` and `<Esc>` close. Input that does
not validate is shown beside the field rather than raised, because a half
typed value is normal.

Tracking ends when the file is written, when the buffer is unloaded, and as
soon as the block stops matching what was rendered. Editing a line by hand
therefore ends the tracking, rather than having that edit overwritten by a
later re-render.

A `mixed` template is not tracked: it lands in two places, and tracking half
of it would be worse than tracking none.

7. INSTANTIATING AN ENTITY                               *hdlsnip-instantiate*

|:HdlSnipInstantiate| reads an entity from elsewhere in the project and writes
its instantiation, rather than having you retype an interface that already
exists.

Entities are found by searching from the project root, identified by `.git`,
`vhdl_ls.toml` or `.hdlsnip.lua`, with files nearer the current buffer offered
first. Generated output and vendor build directories are skipped. An entity
with no ports is skipped too: legal, but there is nothing to instantiate.

Association is always named. Positional association compiles with two ports of
the same type swapped, and the result is found in simulation rather than at
analysis.

With a bang, the port signals are declared as well. They go above the
architecture's `begin` while the instance goes below it, and they carry the
names the instantiation maps them to, so the two halves cannot disagree. The
configured direction suffixes are dropped: a signal driving `wr_en_i` is not
itself an input to anything.

Generic values are substituted into the port subtypes, since the instantiating
scope has no `G_WIDTH` of its own. A generic with no default is mapped to its
own name, which will not analyse -- deliberately, since it is a value you have
to supply.

                                                              *hdlsnip-picker*
The list is shown in a window matching the parameter dialog. Typing narrows
it, `<C-d>` and `<C-u>` page through it and wrap at either end, and `<C-k>`
and `<C-j>` move one entry at a time. `picker_height` sets how many are shown
at once.

A digit narrows like any other character rather than selecting, which is what
lets a name ending in a digit be typed at all.

When `vim.ui.select` has been replaced -- telescope, fzf-lua, snacks -- that
is used instead. `picker` overrides the choice: "hdlsnip" always uses this
window, "ui" always uses `vim.ui.select`.

                                                           *hdlsnip-testbench*
|:HdlSnipTestbench| writes the whole testbench rather than an instantiation: a
signal for every port, a clock generator, a reset release, the DUT wired up
and a stimulus process that stops the run.

Clocks and resets are found by shape rather than by the configured name. A
crossing with `src_clk` and `dst_clk` gets a generator for each, and a reset
whose name ends in `n` is released to `'1'` while one that does not is
released to `'0'`. Matching the configured name exactly produced a testbench
that reported done at time zero on any design that did not use it.

Every input is driven from time zero, or the design starts with `'U'` on its
inputs and nothing downstream means anything.

An empty buffer is used as it stands; otherwise `tb_{name}.vhd` is opened
beside the entity's source. A testbench that already has content is not
overwritten.

8. CONFIGURATION                                       *hdlsnip-configuration*

Calling `setup()` is optional; the defaults are used otherwise. >lua

    require("hdlsnip").setup({
      vhdl_std = "2008",
      keyword_case = "lower",
      indent = "  ",
      clock = { name = "clk", edge = "rising" },
      reset = { style = "async", polarity = "low", name = nil },
      naming = {
        in_suffix = "_i",
        out_suffix = "_o",
        reg_suffix = "_r",
        sig_prefix = "",
        proc_prefix = "p_",
        const_prefix = "C_",
        generic_prefix = "G_",
      },
      vendor = "generic",
      align_ports = true,
      lsp = true,
      picker = "auto",
      picker_height = 10,
      keys = {
        expand = false,
        jump_next = false,
        jump_prev = false,
        field_next = { "<Tab>", "<C-k>" },
        field_prev = { "<S-Tab>", "<C-j>" },
      },
    })
<
                                                       *hdlsnip-config-fields*
vhdl_std        "93" | "2002" | "2008" | "2019"
                Which revision's reserved words apply. A signal called
                `context` is legal under VHDL-93 and not under VHDL-2008.

keyword_case    "lower" | "upper"
                Applies to reserved words only. Identifiers keep the case you
                give them, and predefined types such as `positive` and
                `std_logic` are not reserved words.

indent          One indent level. Spaces or tabs, never mixed.

clock.name      Identifier used for the clock.
clock.edge      "rising" | "falling"

reset.style     "async" | "sync" | "none"
                Also decides the sensitivity list: an asynchronous reset
                appears in it, a synchronous one must not.
reset.polarity  "low" | "high"
reset.name      Derived from polarity when unset: `rst_n` when active low,
                `rst` when active high. Set it to override.

naming          Prefixes and suffixes applied to generated identifiers.

vendor          "generic" | "amd" | "intel" | "lattice" | "microchip"
                Selects vendor attributes such as `async_reg` and `preserve`.

align_ports     Align the columns of generated declarations.

lsp             Offer templates through the in-process completion server.
                See |hdlsnip-completion|.

picker          "auto" | "hdlsnip" | "ui". Which window chooses a template
                or an entity. See |hdlsnip-picker|.

picker_height   How many choices hdlsnip's own picker shows at once.

keys            Mappings created by `setup()`. See |hdlsnip-mappings|.

`setup()` may be called more than once. It is partial: an option it does not
mention keeps its current value, so a later call adding `keyword_case` does
not unset the `keys` an earlier one established.

Invalid options are reported with the path that is wrong, and the previous
configuration is kept rather than half-applied.

9. PROJECT CONFIGURATION                              *hdlsnip-project-config*

A `.hdlsnip.lua` at the project root overrides the global configuration for
buffers beneath it: >lua

    -- .hdlsnip.lua
    return {
      keyword_case = "upper",
      clock = { name = "axi_aclk" },
      reset = { style = "sync", polarity = "high" },
    }
<
The file is arbitrary Lua from a checked-out repository, so it is read through
|vim.secure.read()|: Neovim asks once whether to trust it and remembers the
answer, the same model as 'exrc'. Declining leaves the global configuration in
place.

Derived values are recomputed, not inherited. A project that sets
`reset.polarity = "high"` gets `rst`, not the `rst_n` derived globally.

11. WRITING A TEMPLATE                             *hdlsnip-writing-templates*

Templates are discovered on the 'runtimepath' at: >

    lua/hdlsnip/templates/<lang>/<kind>/<name>.lua
<
Neovim searches your configuration before plugins, so a file at that path in
your own config shadows the one shipped with the plugin. Overriding a template
needs no configuration at all.

The directory must match the template's `kind` and the file name its `name`.
A template that says otherwise is rejected at load, because the picker groups
by kind and a mismatch would file it where nobody looks.

Fields:                                                *hdlsnip-template-spec*

name        Required. lower_snake_case, matching the file name.
kind        Required. skeleton | rtl | cdc | mem | bus | tb.
desc        Required. Shown in the picker.
trig        Optional trigger word, 2 to 12 characters, unique across
            templates, and never a VHDL reserved word: typing `entity` in
            ordinary code must not fire a snippet.
scope       Where the output belongs. See |hdlsnip-scope|.
params      List of parameters. See below.
body        A string with `{{marker}}` substitutions, for a static template.
render      `function(params, cfg): string`, for a dynamic one. Requires
            `dynamic = true`. Mutually exclusive with `body`. May return a
            table instead of a string; see |hdlsnip-scope|.

fixture_declarations
            Optional `function(cfg, params): string[]`. Declarations the
            golden fixture wrapper must add for the output to analyse. See
            |hdlsnip-fixtures|.

external_libraries
            Optional boolean. Set when the output needs a library CI does
            not have, such as VUnit or OSVVM. See |hdlsnip-fixtures|.

Parameters:                                                   *hdlsnip-params*

name        Required, lower_snake_case.
type        string | identifier | integer | number | boolean | choice.
desc        Required. Shown in the prompt.
default     Required.
choices     Required for `choice`; the default must be one of them.
min, max    Bounds for `integer` and `number`.

An `identifier` parameter is checked against the configured VHDL standard, so
a template will not insert a reserved word as a signal name.

In a static body, `{{cursor}}` marks the final tabstop. Every marker must be a
declared parameter and every parameter must appear in the body; both are
checked at load, which catches the rename that updated one and not the other.

Example: >lua

    return {
      name = "counter",
      trig = "cnt",
      kind = "rtl",
      scope = "declarative",
      desc = "Counter register",
      params = {
        { name = "sig", type = "identifier", default = "count",
          desc = "Signal name" },
        { name = "width", type = "integer", default = 8, min = 1,
          desc = "Width in bits" },
      },
      body = "signal {{sig}} : unsigned({{width}} - 1 downto 0);{{cursor}}",
    }
<
                                                               *hdlsnip-scope*
`scope` says where a template's output belongs, which decides where it is
inserted and how it is wrapped for analysis.

design_unit   A complete file: entity, package, context, configuration. The
              default.
declarative   Declarations, for the part above `begin`.
statement     Concurrent statements, for the architecture body.
sequential    Sequential statements, for inside a process.
mixed         Both declarations and statements.

A `mixed` template's render function returns a table rather than a string,
because the two halves go to different places: >lua

    return {
      declarations = "signal count_r : unsigned(7 downto 0);",
      statements = "p_count : process (clk) is ...",
    }

A state machine is the case this exists for: the state type belongs above
`begin` and the processes below it. On insertion the halves are placed either
side of the architecture's `begin`; when the architecture cannot be
identified, both go in at the cursor.

Any other scope returns a plain string, which is treated as `statements`.

                                                            *hdlsnip-fixtures*
Every template is rendered into `tests/golden/` across the configuration
variants and analysed with GHDL. Two fields exist for templates that need
help with that.

A fragment may read signals it does not declare -- an edge detector reads the
signal it watches -- so the wrapper has nothing to analyse. The template says
what to declare, without those declarations reaching the user: >lua

    fixture_declarations = function(cfg, params)
      local sig = (params or {}).sig or "flag"
      return { ("signal %s : std_logic;"):format(sig) }
    end,

`params` carries only what a case overrode, so fall back to the default.

A template whose output needs VUnit or OSVVM cannot be analysed by a plain
GHDL install. Setting `external_libraries = true` writes its fixtures to
`tests/golden/external/`, which the analysis step does not scan. They are
still generated, because they still diff.

12. LUA API                                                      *hdlsnip-api*

                                                             *hdlsnip.setup()*
require("hdlsnip").setup({opts})
        Apply configuration. Optional.

                                                            *hdlsnip.insert()*
require("hdlsnip").insert([{name}, {params}])
        Insert a template. Without {name}, a picker opens. Without {params},
        each parameter is prompted for. Supplying {params} prompts for
        nothing, which is the path for mappings.

                                                            *hdlsnip.expand()*
require("hdlsnip").expand([{name}])
        Expand as a snippet. Falls back to |hdlsnip.insert()| for a dynamic
        template.

                                                  *hdlsnip.expand_at_cursor()*
require("hdlsnip").expand_at_cursor()
        Expand the trigger word before the cursor. When there is no trigger
        but a snippet is active, jumps forward instead. Returns false when
        neither applies, so a mapping can fall through.

                                                            *hdlsnip.reload()*
require("hdlsnip").reload()
        Rescan the runtimepath.

                                                       *hdlsnip.instantiate()*
require("hdlsnip.instantiate").instantiate([{name}, {opts}])
        Instantiate an entity. {opts} takes `signals`, `label`, `library`
        and `component`.

                                                         *hdlsnip.testbench()*
require("hdlsnip.instantiate").testbench([{name}, {opts}])
        Write a testbench around an entity. {opts} takes `period_ns` and
        `library`.

                                                         *hdlsnip.vhdl.entity*
require("hdlsnip.vhdl.entity").parse({lines})
        Read an entity declaration, returning `{ name, generics, ports }`
        or nil and a reason.

                                                           *hdlsnip.edit.at()*
require("hdlsnip.edit").at({bufnr}, {row})
        The tracked block containing {row}, as `id, entry`, or nil.

                                                       *hdlsnip.edit.update()*
require("hdlsnip.edit").update({bufnr}, {id}, {changes})
        Re-render a tracked block with changed parameters. Returns
        `ok, errors`. Leaves the buffer untouched when a change does not
        validate.

                                                         *hdlsnip.form.edit()*
require("hdlsnip.form").edit({bufnr})
        Open the parameter form for the block under the cursor.

                                                 *hdlsnip.registry.register()*
require("hdlsnip.registry").register({tpl})
        Register a template built in Lua rather than discovered from a file.
        Returns `ok, errors`.

                                                              *hdlsnip.render*
require("hdlsnip.render").values({tpl}, {params}, {cfg})
        Render a template as plain VHDL. Returns `text, errors`.

                                                   *hdlsnip.render.sections()*
require("hdlsnip.render").sections({tpl}, {params}, {cfg})
        Render into `{ declarations, statements }`. What `values()` is
        built on, and what a caller placing the halves separately wants.

13. HEALTH                                                    *hdlsnip-health*

`:checkhealth hdlsnip` reports the Neovim version, how many templates were
found and of which kinds, the configuration in effect for the current buffer,
and anything that failed to load, with the reason.

A template that fails validation is skipped rather than aborting the load, so
one broken file in your configuration cannot take the library down. It will be
listed here instead of silently missing.
